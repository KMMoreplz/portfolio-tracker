# Заметки по проекту (рабочие, не часть ТЗ)

## Доступ к БД
- Spring Data JDBC, SQL пишется вручную в репозиториях. Выбрано вместо Hibernate: явные JOIN, нет N+1 и магии с lazy-коллекциями.
- Если где-то появится Hibernate/JPA — обязательно JOIN FETCH в запросах с коллекциями, иначе N+1 по запросу на каждую запись.

## Позиционирование
- У Snowball Income нет ограничения по количеству бумаг — сервис просто платный (подписка после пробного периода).
- Ключевая идея проекта: бесплатно и без подписки, отслеживать столько бумаг, сколько есть на счёте, с полным разбором сделок и комиссий.

## Разбор Snowball Income: как устроено и что берём себе

Источники: ru.help.snowball-income.com (обзор возможностей, «Среднегодовая доходность» (XIRR), «Импорт отчетов брокера», «Интеграция Tinkoff API»), обзор сервиса (vk, 2024), описания в App Store / Google Play / RuStore.

Как устроено:
- Модель: Портфель → Категории (дерево «папок» с целевыми долями в %) → Активы (акции, облигации, фонды/REIT, металлы, валюта, крипто, произвольные) → Сделки + Начисления. Портфелей может быть несколько, есть составной портфель («Мой капитал»).
- Импорт: брокерские отчёты (30 брокеров, повторная и пересекающаяся загрузка не дублирует сделки) или API Тинькофф (токен «Все счета, только чтение», автосинк дважды в день), Binance, JetLend.
- Метрики главной: Стоимость, Вложено, Прибыль (дивиденды + продажи − комиссии − налог с дивидендов), Доходность (XIRR — среднегодовая при переменных пополнениях), Рост активов, Пассивный доход (прогноз выплат на год вперёд, только регулярные).
- Дивиденды: календарь (ожидаемые/фактические), прогноз на год, рост выплат компаний, рейтинг дивидендов.
- Прочее: сравнение с индексами (S&P 500, MOEX, NASDAQ), коэффициент Шарпа, диверсификация по секторам/странам, цели, мультивалютность, валютная переоценка, демо-портфель.
- Тарифы: платный (≈350 ₽/мес); бесплатный — ограничен (1 портфель, до ~15 активов по обзору 2024).

Берём себе: XIRR (доходность при нерегулярных пополнениях), дивидендный календарь с прогнозом на год, учёт комиссий и налога с дивидендов в прибыли, валютная переоценка (курсы ЦБ), категории с целевыми долями (ребалансировка), сравнение с индексами.

Не берём: рейтинг дивидендов (нужна финансовая отчётность компаний), импорт брокерских отчётов (у нас прямой API — это и есть фишка), раскрытие состава фондов, произвольные активы (недвижимость/вклады), мобильное приложение.

## План работ

1. Каркас: монорепо Maven, docker-compose с PostgreSQL, Flyway-схема (пользователи, инструменты, операции, комиссии, выплаты, позиции).
2. `broker-sync-service`: клиент T-Invest API (песочница), выгрузка счетов, инструментов, всех операций, идемпотентные апсерты.
3. Аналитика: позиции, средние цены с комиссиями, реализованный и нереализованный P&L, потери на комиссиях, дивиденды и купоны.
4. `portfolio-service`: REST API и веб-дашборд (бумаги, сделки, комиссии, дивидендный календарь, график стоимости).
5. `telegram-bot-service`: уведомления о выплатах и дайджест портфеля.
6. Сквозные улучшения (раздел «Сквозные улучшения» в README): тесты и CI/CD, Kafka, наблюдаемость, новости, индексы.

## Трудности и решения

1. Повторная синхронизация может задублировать операции. Каждая операция сохраняется апсертом по идентификатору операции, в базе хранится курсор последней выгрузки: следующий запуск дотягивает только новые операции, полная пересинхронизация безопасна.
2. Сертификаты T-Bank. `*.tbank.ru` выпускается НУЦ Минцифры, которого нет в стандартных truststore; корневой сертификат добавляется в truststore JVM, иначе клиент падает с `SSLHandshakeException`.
3. Лимиты и сбои API брокера. Rate limiter уважает лимиты запросов на токен, retry с экспоненциальным backoff сглаживает сетевые сбои, circuit breaker не даёт недоступному API брокера развалить веб-часть.

## Соглашения по коду

Имена проектов и сервисов — kebab-case, классы — CamelCase, поля и методы — lowerCamelCase, константы — SCREAMING_SNAKE_CASE. Сокращения в именах не используются, имя отражает содержимое. Суффиксы классов отражают слой: `Service`, `Controller`, `Repository`, `Dto`, `Config`. Поля приватные, доступ через методы. Код отформатирован как после Ctrl+Alt+L в IDEA. Группы: `com.mikhail`, пакеты сервисов: `com.mikhail.portfolio`, `com.mikhail.brokersync`, `com.mikhail.telegrambot`.

## Технические заметки (Spring Boot 4.1, сборка)

- Auto-configuration в Boot 4 разнесён по модулям: Flyway не подключается одним `flyway-core` — нужен `org.springframework.boot:spring-boot-flyway`, иначе миграции молча не выполняются и падают SQL-запросы («relation does not exist»).
- Тестовые аннотации переехали: `@AutoConfigureMockMvc` теперь в `org.springframework.boot.webmvc.test.autoconfigure`, сама поддержка MockMvc — в модуле `spring-boot-starter-webmvc-test` (spring-boot-starter-test его больше не тянет).
- Jackson 3: пакеты `tools.jackson.databind` (`ObjectMapper`, `JsonNode`), а не `com.fasterxml.jackson.databind`.
- Суммы в ответах API сериализуются как числа с масштабом столбца (`10.00000000` у `NUMERIC(20,8)`) — точность сохраняется, double нигде не используется.
- Скрипт `mvn` из дистрибутива под MSYS/git-bash конвертирует пути через cygpath в POSIX, которые nativ-`java.exe` не понимает («Could not find or load main class org.codehaus.plexus.classworlds.launcher.Launcher»). Обходной путь: обёртка `C:\Users\Mi\tools\bin\mvn`, вызывающая java напрямую с Windows-путями; Maven 3.9.16 лежит в `C:\Users\Mi\tools\apache-maven-3.9.16`.
- curl с кириллицей в `-d` из этой консоли уходит в неверной кодировке и падает валидацией Jackson; кириллицу в тело запроса подавать файлом (`-d @file.json`, UTF-8).

## Сквозные улучшения — зачем каждое

Каждый пункт — строка из правил оценивания курса; затрагивают всё приложение и подключаются поверх ядра в любом порядке.

- Тесты (JUnit 5 + Testcontainers) и CI (GitHub Actions): проверки идут на настоящей PostgreSQL в Docker, а при каждом push в репозиторий сборка и тесты запускаются автоматически — сломанное видно сразу, а не когда код уже уехал.
- Kafka между broker-sync-service и portfolio-service: асинхронное взаимодействие — выгрузка кладёт сообщения в очередь, ядро обрабатывает их, когда готово; сбой или перегрузка одного сервиса не останавливает другой.
- Наблюдаемость (Actuator, Prometheus, Grafana): Actuator отдаёт метрики сервиса (живость, ошибки, время ответов, обращения к API брокера), Prometheus собирает их в временные ряды, Grafana рисует графики — видно, когда и как приложение деградировало.
- Контейнеризация всех сервисов и размещение на домене: запуск одной командой, доступ извне.
- Новости по бумагам из портфеля (парсинг RSS): контент для дашборда.
- Сравнение доходности с индексами (MOEX, S&P 500): насколько портфель лучше или хуже рынка.
- Категории активов с целевыми долями и отклонением от них (ребалансировка): планирование структуры портфеля, как в Snowball Income.
- Курсы валют ЦБ для пересчёта портфеля в одну валюту: мультивалютный портфель одной суммой.
